# Enterprise Documentation Standard

Apply these rules to every document generated by `ai-init` or a companion
skill. They make documentation auditable, maintainable, and usable by both
people and AI agents. Repository-specific instructions take precedence when
they are stricter.

## Document control

Every generated project document includes a control line immediately after the
H1 title:

```text
> **Document control** — Owner: <owner or Not documented> · Status: Draft |
> Reviewed | Approved · Version: <MAJOR.MINOR.PATCH> · Last reviewed:
> YYYY-MM-DD · Classification: Public | Internal | Confidential | Restricted
```

Rules:

- Use `Draft` unless a human review or approval is recorded. Never infer
  approval from code review, CI success, or an agent run.
- `Last reviewed` is the date evidence was inspected, not the date the file was
  last formatted.
- Classification follows the organization's scheme. If no scheme is confirmed,
  use `Internal` for operational detail and `Public` only for content that is
  already public.
- Record the source of truth (repository path, commit, external system) when it
  is not obvious.

## Evidence provenance

Every substantive claim is one of:

| Type | Meaning | Required support |
|---|---|---|
| Verified | Reproduced from the current commit | Exact path, command, or result |
| Observed | Visible in code/configuration but not executed | Path and interpretation |
| Planned | Confirmed intent not yet implemented | Decision or issue reference |
| Not documented | No reliable evidence | Explicit statement |
| Not assessed | Review did not cover it | Scope limit |

- Record the reviewed commit SHA and inspection date in the document or its
  control block.
- Do not present generated prose, old documentation, comments, or file names as
  proof that behavior is active.
- Inferences must be labeled as inferences and must name the evidence.
- When evidence conflicts, surface the conflict rather than choosing silently.

## Normative language

Use RFC 2119 and RFC 8174 keywords deliberately:

- `MUST` / `MUST NOT` — mandatory requirement.
- `SHOULD` / `SHOULD NOT` — recommended; an exception requires a stated reason.
- `MAY` — genuinely optional.

Define the keyword convention once near the top when a document uses it, and do
not use these words for aspirations, observations, or marketing. Lowercase
"must" in ordinary prose is acceptable only when unambiguous.

## Document classes (Diátaxis)

| Class | Purpose | Test |
|---|---|---|
| Tutorial | Teach a beginner through a working example | Can a new user finish it without prior context? |
| How-to guide | Solve a specific task | Does it assume competence and focus on steps? |
| Reference | State facts precisely | Is it complete, structured, and free of narrative? |
| Explanation | Give context and rationale | Does it answer why rather than how? |

Do not mix a tutorial, full reference, and design rationale in one page. Link
between classes instead. The README is an index, not a tutorial.

## Decisions

Use an ADR/MADR-style record:

```text
### D-12 — Short decision title

- Status: Proposed | Accepted | Superseded | Deprecated
- Date: YYYY-MM-DD
- Owner: <role or Not documented>
- Context: the forces and constraints
- Decision: what was chosen
- Consequences: positive, negative, and follow-up work
- Alternatives rejected: option and why
- Supersedes / superseded by: D-XX or None
- Evidence: path, issue, or meeting record
```

Preserve permanent IDs. Mark a decision superseded rather than deleting it. Do
not invent rationale or rejected alternatives; write `Not documented`.

## Architecture

Follow ISO/IEC/IEEE 42010:2022 concepts: stakeholders, concerns, viewpoints,
views, and correspondences.

- Use C4-style levels when they fit: system context, container, component, and
  code. Do not draw all levels if one view answers the current question.
- Show trust boundaries, external dependencies, data stores, and deployment
  targets that affect security or operations.
- Label each diagram with its scope and viewpoint. Every node and edge must be
  traceable to code, configuration, or a confirmed decision.
- Include quality attributes and known constraints. arc42 or a similar
  structure may supply the section checklist; do not copy its boilerplate
  without content.

## Naming and file layout

| Location | Convention | Examples |
|---|---|---|
| Repository root | Uppercase meta files | `README.md`, `LICENSE`, `SECURITY.md`, `CONTRIBUTING.md`, `CHANGELOG.md` |
| `docs/` | Lowercase kebab-case | `architecture.md`, `decisions.md`, `security.md`, `tests.md` |
| Acronym exception | Established uppercase acronym | `PRD.md` |
| References | Mirror the source category | `docs/references/style/`, `docs/references/architecture/` |

Avoid spaces, dates, personal names, and version numbers in filenames. Use
Git history or the document control block for dates and versions. Detect
existing names case-insensitively and migrate deliberately; never leave two
competing indexes.

## Page and content quality

- One H1 per page; heading levels must not skip.
- Lead with a plain-language summary for non-specialists, then technical detail.
- Expand acronyms at first use in each document.
- Use tables for structured comparison and keep cells short.
- Use descriptive link text; never "click here" or a raw URL as the only label.
- Provide alt text for meaningful images and a text explanation for diagrams.
- Do not use color alone to convey meaning.
- Keep paragraphs and lists scannable; avoid duplicating the same fact in
  multiple documents. Link to the canonical location instead.
- Remove placeholders before delivery. `TBD` is allowed only for a real,
  acknowledged unknown.

## Accessibility of documentation

- Ensure headings form a logical outline for screen-reader navigation.
- Use table header rows and avoid complex merged cells.
- Give every Mermaid diagram a preceding sentence that states its purpose and
  a following sentence that states the key takeaway.
- Keep diagram labels short and legible at normal zoom.
- Do not embed critical information only in an image or screenshot.

## Versioning, changelog, and review

- Apply Semantic Versioning to released products and to this skill collection.
- Maintain `CHANGELOG.md` using Keep a Changelog categories: Added, Changed,
  Deprecated, Removed, Fixed, Security.
- Record documentation changes that affect requirements, contracts, or
  operations; typo fixes do not require an entry.
- Set a review cadence by risk: security and architecture documents at least
  quarterly, operational runbooks more often, stable reference pages annually.
- On review, re-verify commands, paths, links, owners, and control statuses.
  Update the control block only after the review is complete.

## Data handling

- Never include credentials, tokens, private keys, session identifiers,
  customer records, or unredacted personal data.
- Cite configuration keys and secret-store paths, not secret values.
- Use synthetic examples and reserved domains (`example.com`), documentation
  IP ranges (`192.0.2.0/24`), and clearly fake identifiers.
- Follow the organization's data-classification and retention policy when
  quoting logs, screenshots, or production evidence.

## Delivery checklist

- Frontmatter, IDs, and document control are intact.
- Every claim is verified, observed, planned, or explicitly unknown.
- Links resolve; no skipped optional document is linked.
- No placeholders, secrets, or personal data remain.
- Accessibility basics are satisfied.
- README index matches the files that exist.
- Review status is honest.
