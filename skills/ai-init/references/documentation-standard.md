# Enterprise Documentation Standard

Apply these rules to every document generated by `ai-init` or a companion
skill. They make documentation accurate, maintainable, and easy to use.
Repository-specific instructions take precedence when they are stricter.

## Claim status

Every substantive claim is one of:

| Type | Meaning |
|---|---|
| Verified | Reproduced from the repository as inspected; a path, command, or run supports it |
| Observed | Visible in code or configuration but not executed |
| Planned | Confirmed intent that is not implemented yet |
| Not documented | No reliable support found |
| Not assessed | The review did not cover it |

- Do not add a provenance header naming a branch, revision, or tool version.
  Cite the path, command, or result that supports each claim instead.
- Describe the state that exists now, not a snapshot of the last run. Do not
  copy values the configuration already owns — exact version pins, hook
  revisions, test counts, run dates, coverage percentages — because duplicates
  drift. Link the file that owns the value: `.pre-commit-config.yaml`,
  `requirements-dev.txt`, the workflow, or the manifest. A decision record may
  quote the value it chose; a description of current behavior must not.
- Do not present generated prose, old documentation, comments, or file names as
  proof that behavior is active.
- Inferences must be labeled as inferences and must name the file, command,
  or record they rest on.
- When sources conflict, surface the conflict rather than choosing silently.

## Normative language

Use RFC 2119 and RFC 8174 keywords deliberately:

- `MUST` / `MUST NOT` — mandatory requirement.
- `SHOULD` / `SHOULD NOT` — recommended; an exception requires a stated reason.
- `MAY` — genuinely optional.

Define the keyword convention once near the top when a document uses it, and do
not use these words for aspirations, observations, or marketing. Lowercase
"must" in ordinary prose is acceptable only when unambiguous.

## Document classes (Diátaxis)

| Class | Purpose | Test |
|---|---|---|
| Tutorial | Teach a beginner through a working example | Can a new user finish it without prior context? |
| How-to guide | Solve a specific task | Does it assume competence and focus on steps? |
| Reference | State facts precisely | Is it complete, structured, and free of narrative? |
| Explanation | Give context and rationale | Does it answer why rather than how? |

Do not mix a tutorial, full reference, and design rationale in one page. Link
between classes instead. The README is an index, not a tutorial.

## No bookkeeping metadata

A table states a subject and a finding. It does not carry per-row bookkeeping,
and a record does not carry paperwork that no process consumes.

- Do not add a column for status, date, owner, evidence, verification,
  baseline, target, or measure.
- Do not record rejected options or supersession as fields. If a decision is
  replaced, the replacing record names the one it replaces.
- When a table has to say whether something holds, use at most one column
  named `Assessment`, or `Coverage` for requirement traceability, and put the
  claim and its basis in that cell.
- The record of when and why a change happened is the commit and the pull
  request, not a field in the document.

## Titles and links

The default output is a project README and the `docs/` set. A root
`AGENTS.md` symlink may be created separately when it does not replace existing
instructions. Every other document is created only when the repository
supports it, so the output set differs per repository.

- Treat the root README as ordinary project documentation. Do not describe it
  as an entry point for AI or agents, label its audience as people or humans,
  link it to `AGENTS.md`, or copy skill instructions into it.
- A title names the document type, not the project. Do not carry a project name
  in an H1 and do not suffix it with a separator: `# Architecture`, not
  `# Architecture — <project>`.
- Link only to a document that exists. A generated page may link any document
  in its own repository; a link to a skipped document is a broken link.
- A template contains no relative link. It is copied into another repository, so
  a link inside it resolves against this repository's layout, where the target
  does not exist. Name the document in a code span and let the skill write the
  link when it writes the document.
- A related-document footer is written as
  `{{RELATED_DOC_LINKS_TO_EXISTING_FILES_OR_NONE}}`. Replace it with links to the
  documents that were actually written, and delete the section when none remain.
- A template never links into the skill tree either. `references/` ships with the
  skill, not with the repository it documents, so state the rule inline and show
  any required code block in the template itself.
- An index row names a document and its file in parentheses; the skill turns the
  name into a link and deletes the parenthetical. Keep only rows for documents
  that exist, and delete the instruction paragraph once the page is written.

## Decisions

Use a short ADR-style record:

```text
### D-12 — Short decision title

- Context: the forces and constraints
- Decision: what was chosen
- Consequences: positive, negative, and follow-up work
- Reason: the rationale, or Not documented
```

Preserve permanent IDs and never delete or renumber a record. Do not invent a
rationale; write `Not documented`. When a record is replaced, the new record
names the one it replaces.

## Architecture

Follow ISO/IEC/IEEE 42010:2022 concepts: stakeholders, concerns, viewpoints,
views, and correspondences.

- Use C4-style levels when they fit: system context, container, component, and
  code. Do not draw all levels if one view answers the current question.
- Show trust boundaries, external dependencies, data stores, and deployment
  targets that affect security or operations.
- Label each diagram with its scope and viewpoint. Every node and edge must be
  traceable to code, configuration, or a confirmed decision.
- Draw the diagram rather than filling in a blank. A Mermaid block is rendered
  as written, so a template token inside it is a syntax error. A template may
  carry a valid example diagram that defines the init line; the skill replaces
  its example nodes with verified evidence, or deletes the block and states why
  the view is omitted.
- Include quality attributes and known constraints. arc42 or a similar
  structure may supply the section checklist; do not copy its boilerplate
  without content.

## Naming and file layout

| Location | Convention | Examples |
|---|---|---|
| Repository root | Uppercase meta files | `README.md`, `LICENSE`, `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` |
| `docs/` | Lowercase kebab-case | `architecture.md`, `decisions.md`, `security.md`, `tests.md` |
| Acronym exception | Established uppercase acronym | `PRD.md` |
| References | Mirror the source category | `docs/references/style/`, `docs/references/architecture/` |

Avoid spaces, dates, personal names, and version numbers in filenames. Use Git
history for dates and versions. Detect
existing names case-insensitively and migrate deliberately; never leave two
competing indexes.

## Page and content quality

- One H1 per page; heading levels must not skip.
- Lead with a plain-language summary for non-specialists, then technical detail.
- Expand acronyms at first use in each document.
- Use tables for structured comparison and keep cells short.
- Use descriptive link text; never "click here" or a raw URL as the only label.
- Provide alt text for meaningful images and a text explanation for diagrams.
- Do not use color alone to convey meaning.
- Keep paragraphs and lists scannable; avoid duplicating the same fact in
  multiple documents. Link to the canonical location instead.
- Remove placeholders before delivery. `TBD` is allowed only for a real,
  acknowledged unknown.

## Accessibility of documentation

- Ensure headings form a logical outline for screen-reader navigation.
- Use table header rows and avoid complex merged cells.
- Give every Mermaid diagram a preceding sentence that states its purpose and
  a following sentence that states the key takeaway.
- Keep diagram labels short and legible at normal zoom.
- Do not embed critical information only in an image or screenshot.

## Review and change management

- Change history lives in Git and in the pull request that makes the change.
  Do not add a changelog or per-document version number unless the project has
  adopted a release policy that requires one.
- Record documentation changes that affect requirements, contracts, or
  operations in the pull request description.
- Set a review cadence by risk: security and architecture documents at least
  quarterly, operational runbooks more often, stable reference pages annually.
- On review, re-verify commands, paths, links, and control descriptions.
- An existing document is a previous snapshot, not an authority. Re-derive its
  statements from the current tree, correct what no longer matches, and add what
  appeared; a file is never current merely because it exists.

## Data handling

- Never include credentials, tokens, private keys, session identifiers,
  customer records, or unredacted personal data.
- Cite configuration keys and secret-store paths, not secret values.
- Use synthetic examples and reserved domains (`example.com`), documentation
  IP ranges (`192.0.2.0/24`), and clearly fake identifiers.
- Follow the organization's data-classification and retention policy when
  quoting logs, screenshots, or production evidence.

## Delivery checklist

- Frontmatter and requirement IDs are intact.
- Every claim is verified, observed, planned, or explicitly unknown.
- Links resolve; no skipped optional document is linked.
- No placeholders, secrets, or personal data remain.
- Accessibility basics are satisfied.
- README index matches the files that exist.
- The claim vocabulary is used honestly and no row is left unstated.
